# L4 WPF launcher implementation plan

**Goal.** Turn the approved English dark-olive mockups in [L3 PR #1](https://github.com/Flinterino/wz-sync/pull/1) into a Windows app on the L2 Core API. This PR is based on Core PR #2.

**Architecture.** WPF manages selection, review, progress, and the manual CurseForge handoff. A small session class retains the immutable plan shown to the player and serializes operations. Core remains responsible for planning, checking bytes, applying, journaling, and restoring.

## 1. Check a release without writing

- Add `ReleaseManifestClient` and `PackChoice` in `src/WzSync.Core/ReleaseManifestClient.cs`. Map Full and Lite to fixed filenames. Start at the latest-release asset route, accept the tagged asset route in the same repository, and use that tag for the checksum request. Reuse the Core HTTPS and raw redirect checks, with GitHub release asset hosts as the only cross-host destinations.
- Limit each response body, check the generated SHA-256 sidecar against exact manifest bytes, decode UTF-8, parse with Core, and require the requested pack. Never persist the response or tell the player its publisher was authenticated.
- In `tests/WzSync.Core.Tests/ReleaseManifestTests.cs`, use an in-memory HTTP handler to verify pinned tag pairing, invalid redirects, wrong checksum and size, missing assets, and wrong-pack rejection. Run the Core Release suite on both OS targets.
- Add a read-only pending-recovery check, validated local log browsing, and optional transaction progress in Core. Write tests for the profile remaining untouched before approval, and the transition from downloads to managed mutation.

## 2. Select and approve a specific plan

- Add `src/WzSync.App/ProfileSelection.cs` and `SyncSession.cs`. Discover immediate profile folders in the default CurseForge Instances directory and accept Browse for custom folders. Validate an existing local instance folder and its CurseForge marker without reading marker contents. No profile files are created by selection, check, or restore preview.
- Clear the pending plan on selection changes, check, cancel, restore, recovery, and apply attempts. Only apply the exact visible plan object, and block required manual files. Use the engine to recheck on-disk contents, preserve recovery, and reject stale approval. Recover only after an affirmative player action.
- Add `tests/WzSync.App.Tests` for no-write discovery and preview, stale or manual denial, busy-state exclusion, an approved apply/restore round trip, and permitted handoff links. Use temporary profiles and fake release HTTP. Test browser link and existing log-folder validation independently of shell execution.

## 3. Implement the approved WPF screens

- Add `App.xaml`, `MainWindow.xaml`, and its code-behind in `src/WzSync.App`. Preserve the setup, review, staging, applying, done, error, and restore flow. Show all actions and both sizes, source host, an explicit official-page action, and a toggle for both full hashes. Label an installed version as unknown when Core has no verified previous version.
- Let the player cancel checking or staging. Disable selection, restore and other operations while work is active. Core finishes or recovers a transaction after the commit boundary. Require a fresh check after restore or a failed apply.
- Provide the local log viewer and open its existing folder. Present the CurseForge Play instruction when no verified profile deep link is available. No app installer, background service, registry changes, game launch, telemetry, or automatic retries of a modified plan.
- Exercise the native WPF window and review keyboard controls, contrast, scroll behavior, and English flow. Verify build with the pinned .NET 10 SDK. Publish a self-contained win-x64 build locally for verification where the runtime pack is available.

## 4. Verify and submit

- Add the WPF app and test project to `WzSync.slnx`. Keep Core tests on Ubuntu and Windows, run app tests on Windows, and enable PR checks for the stacked Core base branch. Keep Action revisions pinned and permissions read-only.
- Document how to run and verify L4. Independently review file and network scope, approval, cancellation, restore and log handling. Run Release tests and a public privacy scan before pushing. Open one stacked PR and confirm exact-head checks on both platforms. Leave merge, main retargeting, release publication and real-profile/game verification to their respective stages.
