# L5 launcher release implementation plan

**Goal.** Build and verify one Windows x64 executable from a release tag. Pair it with the approved Full and Lite release bundle and append the executable and checksum to the same GitHub draft.

**Release source.** The approved bundle comes from the pack builder. It consists of both manifest and checksum pairs plus precisely the owned assets referenced by the manifests. The owner or authorized release operator stages those assets in a draft with the exact manifest version as its tag. Claude reviews the release inputs and the tagged build. Publication is a separate action.

## 1. Validate a release bundle offline

- Reuse Core's tagged-manifest verification when checking the bundle in `tools/WzSync.Release`. Require the requested Full and Lite pack, exact tag, valid SHA-256 sidecars, existing managed path policy, and approved source URLs.
- Inventory the flat directory before opening payloads. Require canonical names and ordinary files. Refuse symlinks, directories, case collisions, missing assets, extraneous assets, and disagreements about size or SHA-256. Treat JARs as opaque bytes. The approved upstream manifest determines asset provenance.
- Add synthetic tests for valid approval input, invalid manifests and sidecars, missing and extra files, invalid paths and URLs, and altered payloads. Run the Core test project on Ubuntu and Windows.

## 2. Build a reproducible single file

- Add `tools/release/Build-Launcher.ps1`. Snapshot the same Git commit into two fresh source directories. Publish both from the pinned .NET SDK as Windows x64 with an embedded runtime, native extraction, and normalized paths. Require precisely one executable from each publish and compare byte length and SHA-256.
- Copy one verified executable and write its release checksum into a new output folder. Pass the verified hash to the draft job through a workflow output. Run this same smoke build on pull requests and tags.

## 3. Attach only to an approved draft

- Add a tag workflow with full-SHA official actions. Prepare the executable in a read-only job after the Core and WPF tests. Limit write permission to the separate draft attachment job.
- In `tools/release/attach_draft.py`, use the fixed GitHub repository, strict tag validation and numeric asset IDs. Verify the GitHub tag resolves to the checked-out commit. Require an existing draft. Validate all asset names before downloading into an empty temporary directory and pass it through the offline validator.
- Recheck the draft identity and input assets before upload. Attach only the tested executable and its checksum. An existing matching output can be reused; refuse conflicts. Append through the exact verified release ID. Do not create, publish, delete, or overwrite a release, tag, or asset in automation.
- Test the draft selection, safe asset set, verified launcher bytes and append-only behavior with a fake GitHub transport. The tests stage no public data.

## 4. Verify and submit

- Document the player workflow, checksum commands, unsigned SmartScreen behavior, limits of checksum verification, and the .NET temporary runtime extraction directory.
- Run an offline package dry run with synthetic fixtures and reproduce the executable from two clean snapshots. Get an independent specification and security review before pushing the single L5 PR, stacked on L4. Verify Release checks for the exact PR head.
- Keep tagged draft acceptance pending until the approved upstream bundle is available and all third-party publication permissions are resolved. Keep fixture manifests off GitHub Releases.
